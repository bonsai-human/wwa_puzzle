# wwa_puzzle 設計ドキュメント

WWA（World Wide Adventure）系の見下ろし2Dパズルゲーム。
GitHub Pages 上で動作する静的Webアプリとして実装する。

本書は実装前の設計仕様であり、実装はまだ行っていない。

---

## 1. ゲームの本質

マップ上のリソース（HP・攻撃力・防御力・鍵・オーブ）をどの順序で回収し、
どの敵を倒し、どの扉を開けるかを決める**完全情報のリソース配分パズル**である。

決定的（乱数なし）、完全情報、有限状態。プレイヤーは「詰将棋を解く」ことになる。

重要な帰結として、**プレイヤーは死なない**。HPが0になる戦闘は発生せず、
単にその敵を通過できないだけである。したがって敗北とは「ゴールへ到達する手順が
存在しなくなった状態」＝**詰み**を意味する。プレイヤー自身は詰みに気づけないため、
ソルバーによる詰み検出がゲーム体験の一部になる。

パズルの深さを生む要素は次の4つ：

| 要素 | 生まれる判断 |
|---|---|
| HPが有限で、撃破にHPを消費する | どの敵に払うか |
| 攻撃力・防御力が撃破コストを非線形に変える | どの順で強化するか |
| 扉と鍵が経路を閉じる | どの鍵をどの扉に使うか |
| オーブは撃破でしか手に入らず、強化と排他交換される | 通る必要のない敵を倒すか |

特にオーブは「倒す必要のない敵を、倒す価値のあるものに変える」装置として機能する。
これがないと最適戦略が「道を塞ぐ敵のうち払える相手だけ倒す」に収束し、選択が痩せる。

## 2. 用語

| 用語 | 定義 |
|---|---|
| セル | マップの1マス。座標 `(x, y)`、内部インデックス `i = y * width + x` |
| 地形 (terrain) | 床 or 壁。**永久に不変** |
| オブジェクト (object) | セルに置かれた敵・アイテム・扉・祭壇。解決されると消滅する（祭壇を除く） |
| 解決 (resolve) | オブジェクトのあるセルへ進入しようとしたときに走る判定 |
| 消費済み集合 (consumed) | 解決済みオブジェクトのセル集合。単調増加する |
| 通行可能 (passable) | 床であり、かつオブジェクトが無い（＝元から無い、または消費済み）セル |
| 自由領域 (region) | 現在位置から、追加の解決なしに到達できるセルの連結成分 |
| 関門 | 主経路上に置かれ、リソースを要求する敵または扉 |

## 3. コアルール仕様

### 3.1 マップと移動

- 幅 `width` × 高さ `height` の直交グリッド。
- 移動は上下左右の4方向、1手1マス。斜め移動なし。
- マップ外・壁への進入は不可。
- 通行可能セルへの進入は無条件に成功する。
- オブジェクトのあるセルへの進入は、**解決に成功した場合のみ**成功する。
  失敗した場合、プレイヤーは動かず、状態は一切変化しない（HPも減らない）。

### 3.2 戦闘

プレイヤー先手の交互ターン制。乱数なし、整数のみ。

```
dp = player.atk - enemy.def        自分が1発で与えるダメージ
de = enemy.atk  - player.def       敵が1発で与えるダメージ

dp <= 0                    → 攻撃不能。このセルは永久に通過できない
n    = ceil(enemy.hp / dp)         撃破に必要な自分の手数
cost = (n - 1) * max(0, de)        敵の反撃回数は n-1 回

player.hp >  cost          → 勝利。hp -= cost、オーブを獲得、敵は消滅
player.hp <= cost          → 通過不能（戦闘は発生しない）
```

**設計上の要点**

- 最後の一撃で敵は倒れるため反撃しない。よって反撃回数は `n` ではなく `n - 1`。
- `de <= 0` のとき被害は0。防御力を先に上げると特定の敵が無料になる。これは意図した設計であり、
  「防御ラインを1超えると世界が変わる」という発見の快感を生む。
- 生存条件は `hp > cost`（`>=` ではない）。戦闘後のHPは最低1。
- ループを回さず閉じた式で求まるため O(1)。ソルバーが数百万回評価しても問題にならない。
- **戦闘の実装は必ず1箇所に集約する。** ゲーム本体・ソルバー・自動生成の三者が同じ関数を呼ぶ。
  ここが分岐すると「ソルバーは解けると言ったのに実機で解けない」が確実に起きる。

**順序依存の例**（自 ATK 12 / DEF 2、敵 HP 30 / ATK 10 / DEF 4）

| | dp | n | cost |
|---|---|---|---|
| そのまま戦う | 8 | 4 | **24** |
| 先に攻撃力+4を取ってから戦う | 12 | 3 | **16** |

この 8 の差分の積み上げがパズルの本体である。

### 3.3 アイテム

進入すると効果を適用してセルから消える。取得は常に成功する。

| 効果 | 内容 |
|---|---|
| `hp` | HPを加算。**上限なし** |
| `atk` | 攻撃力を加算 |
| `def` | 防御力を加算 |
| `key` | 指定色の鍵を加算 |
| `orb` | オーブを加算（マップ側で任意に配置可能） |

HPに上限を設けない理由：上限があると「回復アイテムを取る順序」に溢れ判定が絡み、
ルールが複雑になる割にパズルとしての面白みが増えない。

### 3.4 扉と鍵

- 扉は色 `key: KeyColor` を持つ。対応する色の鍵を1本消費して開く。開いた扉は消滅する。
- 鍵が無ければ進入不可。
- **マスターキー**の挙動はマップ設定 `masterKeyMode` で切り替える。

| モード | 挙動 | 設計上の性質 |
|---|---|---|
| `permanent`（既定） | 恒久フラグ。以後すべての扉を無償で開ける | 原典に近い強力な報酬。取得以降、扉による制約が消える |
| `wildcard` | 任意色の扉を1枚開ける鍵として枚数で保持 | 制約が消えず、扉パズルを最後まで維持できる |

`permanent` を使う場合、マスターキー取得は**ゲームの相転移点**になる。
自動生成器はこれを認識し、取得後の区間では扉を主要な関門として使わないこと。

`wildcard` モードで色鍵とマスターキーの両方を持っている場合、
どちらを使うかは原理的には分岐だが、探索が膨らむため
**色鍵を優先し、無い場合にのみマスターキーを使う**という簡約を採る。
この簡約は最適性を厳密には保証しないため、既定モードを `permanent` としている。

### 3.5 オーブと祭壇（採用案：単一通貨＋交換所）

- 敵を倒すとオーブを獲得する。既定は1体につき1個。マップ側で敵ごとに変更可能。
- **祭壇**セルに到達するとメニューが開き、オーブを消費して強化と交換できる。
- 祭壇は消費されず、セルに残る。到達可能である限り何度でも利用できる。
- 各交換肢には交換回数上限 `stock` を設定できる（省略時は無制限）。
- 交換肢の効果は `Effect` と同じ型（`atk` / `def` / `hp` / `key` / `masterKey`）。

同一の祭壇に複数の交換肢を置き、`stock` を絞ることで
「攻撃力を取るかマスターキーを取るか」という排他的な一手が作れる。これが本機構の主目的である。

将来拡張として、敵種別ごとに色付きオーブを持たせ、強化ごとに要求色を変える案がある。
掃討対象の選択に意味が出て一段深くなるが、UI・マップ設計・生成器の負荷が上がるため
初版では採用しない。データ形式にはオーブを種別化できる余地を残しておく（§4 の注記）。

### 3.6 勝利条件

ゴールセルへ到達した時点で勝利。明示的な敗北条件は存在しない（§1参照）。

### 3.7 画面分割（ステージ構成）

マップは単一の大きな座標空間として持ち、**表示だけを画面単位に量子化する**。

- 1画面のサイズを `screen = { width, height }` で定義する（既定 16×16）。
- マップ全体のサイズは1画面サイズの整数倍とする（例：3×3画面 = 48×48マス）。
- セル `(x, y)` が属する画面は `(floor(x / screen.width), floor(y / screen.height))`。
- カメラはスクロールせず、**プレイヤーのいる画面にスナップする**。
  画面境界を越える移動が成立した時点で表示が次の画面に切り替わる。

**重要：これは純粋に表示上の概念であり、ルールにもソルバーにも一切影響しない。**
移動・戦闘・連結性はすべて全体座標系の上で処理する。画面境界は座標の区切りでしかなく、
壁でも関門でもない。`core/` は画面の存在を知らない。

この分割によって次が得られる。

- **可読性** — 1画面に敵とアイテムが16×16マス分しか入らないため、盤面を読み切れる。
  スクロールする巨大マップは、パズルとしては単に読みにくいだけになる。
- **段階構造** — 画面が自然な「部屋」として機能し、自動生成の骨格の単位になる（§8.2）。
- **画面境界が関門位置になる** — 画面の縁に壁を敷き、開口部を絞ると、
  そこが自然な関門になる。生成器はこの構造を利用する。

**表示上の扱い**

- 画面の各辺に、隣接画面が存在する場合は方向矢印を表示する（参考画像の ▲▼◀▶ に相当）。
- 画面切り替えは短いスライド演出を入れる。演出中も入力は先行入力として受け付ける。
- 移動の解決が先、画面切り替えは後。倒せない敵が境界の向こう側にいる場合、
  移動が失敗するので画面は切り替わらない。
- **全体マップ表示**を用意する。ただし全画面を最初から見せるのではなく、
  **一度でも訪れた画面のみ**を縮小表示する。
  これが無いと「3画面前にあった青い鍵」を暗記させることになり、
  パズルではなく記憶力の問題になってしまう。未訪問画面を伏せることで探索の楽しみは残る。

## 4. データ形式

マップは静的JSONとして扱う。人間が手で書け、gitのdiffが読め、エディタで往復できることを優先する。

```ts
type KeyColor = string;           // "red" | "blue" など。マップ側で自由に定義

interface MapDef {
  formatVersion: 1;
  id: string;
  name: string;
  width: number;                  // マップ全体の幅（screen.width の整数倍）
  height: number;                 // マップ全体の高さ（screen.height の整数倍）

  screen?: { width: number; height: number };   // 1画面のマス数。既定 16×16。表示専用（§3.7）

  start: Point;                   // 開始位置
  goal:  Point;                   // ゴール位置

  player: {                       // 初期ステータス
    hp: number;
    atk: number;
    def: number;
    keys?: Record<KeyColor, number>;
    orbs?: number;
  };

  masterKeyMode?: 'permanent' | 'wildcard';   // 既定 'permanent'

  // 地形。height 行 × width 文字。'.' = 床、'#' = 壁
  terrain: string[];

  // オブジェクトは疎な配列で保持する
  objects: PlacedObject[];

  meta?: {
    seed?: number;                // 自動生成の再現用
    difficulty?: DifficultyReport;
    author?: string;
  };
}

interface Point { x: number; y: number }

type PlacedObject = Point & ObjectDef;

type ObjectDef =
  | { type: 'enemy'; name?: string; sprite?: SpriteId; hp: number; atk: number; def: number; orb?: number }
  | { type: 'item';  effect: Effect }
  | { type: 'door';  key: KeyColor }
  | { type: 'altar'; id: string; options: AltarOption[] };

type Effect =
  | { kind: 'hp';  amount: number }
  | { kind: 'atk'; amount: number }
  | { kind: 'def'; amount: number }
  | { kind: 'orb'; amount: number }
  | { kind: 'key'; key: KeyColor; amount: number }
  | { kind: 'masterKey'; amount?: number };     // wildcard モードでの枚数。permanent では無視

interface AltarOption {
  id: string;
  label?: string;
  cost: number;                   // 消費オーブ数
  effect: Effect;
  stock?: number;                 // 交換回数上限。省略で無制限
}
```

地形を文字列行で持つのは、エディタを介さずテキストエディタで直接マップを書き起こせるようにするため。
テストの手書きマップはこの形式で書く。

`enemy.orb` を将来 `Record<OrbColor, number>` へ拡張できるよう、
エンジン内部ではオーブ所持数を「単一のスカラ」ではなく **1要素の数値ベクトル**として実装しておく。
色付きオーブ案へ移行する際の変更が局所化される。

### バリデーション

読み込み時に以下を検証し、違反はエラーとして拒否する。

- `terrain` の行数・各行の長さが `height` / `width` と一致
- `width % screen.width === 0` かつ `height % screen.height === 0`
- `start` / `goal` が床であり、オブジェクトが無い
- 全オブジェクト座標が範囲内、壁でない、重複しない
- `enemy.hp >= 1`、全ステータスが非負整数
- 祭壇 `id` が一意、`cost >= 0`
- 数値の上限（例：各値 `< 2^31`）。`dp = 1` かつ `enemy.hp` が巨大だと `n` が発散するため、
  `ceil(hp / dp)` の理論最大値をチェックしておく

## 5. 状態モデル

```ts
interface GameState {
  pos: number;              // セルインデックス
  hp: number;
  atk: number;
  def: number;
  keys: Int32Array;         // 色ID → 本数
  orbs: Int32Array;         // オーブ種別 → 個数（初版は長さ1）
  masterKey: number;        // permanent モードでは 0/1、wildcard では枚数
  consumed: Uint32Array;    // セルのビットセット
  altarUsed: Int32Array;    // 交換肢ID → 使用回数
}
```

### 不変条件（ソルバー設計の根拠）

1. `consumed` は単調増加し、要素が取り除かれることはない。
2. 通行可能セルの集合は単調増加する（オブジェクトを消せば床になる）。
3. **`atk` / `def` / `keys` / `orbs` / `masterKey` は `consumed` と祭壇の交換選択のみで決まり、
   訪問順序に依存しない。**（すべて加算的な効果であるため）
4. **順序に依存する唯一の量は `hp` である。**
5. HPは多いほど良い。HPが減って得をする局面は存在しない。

この 3〜5 が、後述の支配関係と探索の縮約をすべて支えている。

## 7. ソルバー設計

### 7.1 なぜ素朴な探索では駄目か

状態は `(位置, 消費済み集合, HP, …)`。消費済み集合だけで `2^N` あり、素朴なBFSは即座に破綻する。
以下の3段の縮約を積む。

### 7.2 縮約1：位置を状態から消す（マクロ行動探索）

自由領域内での移動は、状態を何も変化させない。
よって**1マスの移動を探索の単位にしない**。

```
展開(state):
  region  = 現在位置からの flood fill（通行可能セルのみ）
  if goal ∈ region: 解に到達
  frontier = region に直交隣接するオブジェクトの集合
  for each obj in frontier:
      if 解決可能(state, obj):
          yield 解決した後の状態（位置 = obj のセル）
  for each altar in region:
      for each 交換肢 in altar:
          if 交換可能(state, 交換肢):
              yield 交換後の状態
```

探索の分岐は「次にどのオブジェクトを解決するか」だけになる。
実マップでは1状態あたりのフロンティアは数個〜数十個に収まり、
1マス移動単位の探索と比べて桁違いに小さい。

### 7.3 縮約2：強制手の即時適用

フロンティアの中に、**HPコスト0かつ厳密に有益**なオブジェクトがあれば、
分岐せず即座に解決してよい。該当するのは、

- すべてのアイテム（効果は非負の加算のみ）
- `dp > 0` かつ `de <= 0` の敵（無料で倒せてオーブが増える）

扉は鍵を消費するため対象外。祭壇の交換もオーブを消費するため対象外。

**正当性**：解決後の状態 A と未解決の状態 B は `consumed(A) ⊃ consumed(B)` かつ
全ステータスが `A >= B` を満たし、§7.4 の支配関係により A が B を支配する。
よって B を探索する必要がない。

この簡約は実マップで探索空間を劇的に削る。多くの局面で分岐が消え、
「本当に選択が発生している場所」だけが探索木に残る。

### 7.4 縮約3：支配関係による枝刈り

> **状態 A が状態 B を支配する条件**
> `consumed(A) ⊇ consumed(B)` かつ、
> `hp, atk, def, 各色の鍵本数, 各種オーブ数, masterKey` のすべてで `A >= B`

**正当性の概略**：B の任意の後続手順を A が模倣できることを示せばよい。

- B の手順に含まれるオブジェクトのうち、A が既に消費済みのものは飛ばす。
  その効果は A のステータスに既に反映されており、飛ばすことで損をしない。
- 未消費のものは、`consumed(A) ⊇ consumed(B)` より A の通行可能集合は B 以上なので到達できる。
- 各戦闘のコストは `atk(A) >= atk(B)`、`def(A) >= def(B)` より A のほうが安いか同じ。
- 各扉は `鍵(A) >= 鍵(B)` より開ける。
- 以上より、A は B と同じ地点に、B 以上のHPで到達できる。∎

**実装**：厳密な部分集合判定は高価なため、二段構えにする。

- **第1段（常時）**：`consumed` のハッシュをキーにしたテーブルを持ち、
  同一の消費済み集合に対してステータスベクトルの Pareto フロントのみを保持する。
  安価で、実マップの大半の重複はここで消える。
- **第2段（任意・未実装）**：`|consumed|` でバケット化し、
  ビットセットの superset 判定を限定的に走らせる。深さや時間予算で制御する。
  挿入が O(n) になるうえ、実マップでの効果を測れていないため入れていない。
  第1段だけでも、同じ集合に別経路で到達した状態はすべて潰れる。
  実測では生成した状態の 55% がここで消えている。

### 7.5 縮約4：緩和による打ち切り

各状態で、通れないことが確実な敵と扉だけを壁とみなした flood fill を行う。
これで到達できない位置にゴールがあれば、その状態は確実に詰みであり即座に捨てられる。

**当初は「すべての敵をコスト0、すべての扉を開放」とみなす案だったが、これは実装して
みると何も刈らない。** 壁は不変なので、そこまで緩めた到達可能性はプレイヤーの位置に
関わらず一定になり、ゴールが壁で囲まれている場合——つまりマップの静的な欠陥——しか
検出できない。

そこで緩和を一段締める。

- **攻撃力の上界**：現在の攻撃力に、未消費の攻撃力上昇（アイテム＋祭壇の残り在庫）を
  すべて足す。この値以上の防御力を持つ敵は、何をしても倒せないので壁と同じ。
- **鍵の上界**：色ごとに、所持数＋未消費の供給を足す。0 の色の扉は開かない。
  マスターキーの供給が残っていれば全色の扉を通れるものとして扱う。

どちらの上界も到達可能性を無視して数え上げるので、実際に達成できる値以上になる。
過大評価は「刈りすぎない」側に効くため、解ける状態を誤って詰みと判定することはない。
鍵の取り合い（同じ色の扉が複数あって鍵が足りない）も無視している。同じ理由で安全側。

同じ集計から**終了時HPの上界**（現在HP＋未消費の回復の総和）も得られる。
これは探索順の決定と、見込みのない枝の切り捨てに使う（§7.6）。

### 7.6 探索アルゴリズムと用途

用途によって要求が違うため、同じ状態空間の上に3つのモードを載せる。

| モード | 用途 | 指定 | 完全性 |
|---|---|---|---|
| 最適解 | 終了時HP最大の手順 | `objective: 'maxHp'`（既定） | 完全（予算内で） |
| 到達判定 | 解の存在・詰み検出・ヒント | `objective: 'firstSolution'` | 完全（予算内で） |
| 高速判定 | 生成ループ中の篩い | `beamWidth` を指定 | 不完全。枝を捨てたら `unknown` |

いずれも同じ最良優先探索で、目的関数と打ち切り方だけが違う。

**優先度には現在HPではなく、§7.5 の終了時HP上界を使う。**
現在HP順に見ると「今はHPが高いが、この先の回復をすでに使い切っている」状態を
延々と展開してしまい、良い解に当たるのが遅れる。その結果、後から上界で捨てるだけの枝に
展開コストを払うことになる。上界は許容的なので、この順序を使っても最適性は失われない。
実測では、この変更だけで展開した状態数が 24x24 のマップで 31216 から 11753 に減った。

HP回復アイテムがあるため経路コストが負になりうるので Dijkstra は使えない。
探索を尽くすことで最適性を担保し、予算を超えたら「未確定」を返す。
**「未確定」を「解なし」と混同しない**こと。生成器はこの区別に依存する。
ビーム幅を指定した場合も、実際に枝を捨てたときだけ打ち切りとして記録する。
「不完全な設定で走らせた」ことと「本当に何かを見落とした」ことは別物である。

### 7.7 ヒントAPI

```ts
interface HintResult {
  status: 'solvable' | 'dead' | 'unknown';
  nextAction?: MacroAction;      // 次に解決すべきオブジェクト
  stepsRemaining?: number;
  finalHp?: number;              // 最適解での終了時HP
  deadReason?: string;           // 詰みの説明（例：唯一の赤鍵を消費済み）
}
```

- プレイヤーの現在状態から到達判定を走らせ、`dead` なら詰みを通知する。
  **頼まれなくても毎手走らせる。** プレイヤーは詰みと「難しいだけ」を自力で区別できないので、
  黙っていると解けない盤面を延々と考え続けることになる。
  直前の手で `solvable → dead` に遷移した場合は「この一手で詰みました」と言い分ける。
- ヒントは段階的に出す。押すたびに一段だけ開く。
  「まだ解ける」→「次はどのあたりか（画面／方角）」→「次に触るマス（盤面に印）」。
  手が変われば段階は0に戻す。前の手の答えを出したままにしない。
- UI をブロックしないよう Worker で実行し、キャンセル可能にする。
  操作が止まってから走らせ（400ms）、連続操作のたびに投げ直さない。

### 7.8 性能方針

**実測（デスクトップ、ランダム配置のマップ25件ずつ、`npm run bench`）**

| マップ | 物体数 | 中央値 | 最悪 |
|---|---|---|---|
| 16×16 | 30 | 0.3ms | 4ms |
| 16×16 | 45 | 0.3ms | 1234ms |
| 24×24 | 60 | 0.4ms | 1528ms |
| 24×24 | 80 | 0.6ms | 730ms |

中央値と最悪値の開きが大きい。大半のマップは一瞬で解け、
ごく一部だけが桁違いに重い。したがって固定の時間予算より、
**中断可能にしておくこと**のほうが効く。

なおこれはランダム配置での数字で、実際に配るマップより難しい。
主経路と関門で構造化されたマップ（§8）は分岐がはるかに少ないので、上限の目安として読む。

**効いた最適化**（いずれも当て推量ではなく計測から）

- 自由領域の走査から近傍計算とクロージャを追い出し、
  近傍索引表と障害テーブル（`blockKind`）の直接参照にした。ここが最大の律速だった。
- **自由領域を差分で更新する。** 解決は通行可能性を増やすだけで減らさないので、
  解決したセルから広がった範囲だけを調べればよい。
  強制手の閉包は生成した状態ごとに走るため、ここで全面走査をすると探索全体を支配する。
- 上界による枝の切り捨てを、自由領域を求める**前**に行う。
  見込みのない枝がゴールに立てるかどうかは結論を変えない。

以上で最悪ケースは 16×16/45物体 で 8.1秒 → 1.2秒、24×24/60物体 で 15.9秒 → 1.5秒。

- ビットセットは `Uint32Array`。状態はプールして GC 圧を下げる。
- ハッシュは消費済み集合の FNV-1a 等で十分。
- 単一 Web Worker から始める。GitHub Pages では COOP/COEP ヘッダを設定できず
  `SharedArrayBuffer` が使えないため、共有メモリ並列は不可（§10）。
  並列化する場合は複数 Worker に探索木を分割し `postMessage` で受け渡す。
- 将来ソルバーだけ Rust → WASM 化する余地を残す。
  `core/` を純粋に保っておけば、同じ仕様を移植して差し替えられる。

**モバイル端末での制約**（§11 の対応デバイス方針から来る要求）

スマートフォンのCPUはデスクトップより桁で遅く、モバイルブラウザは
メモリを使いすぎたタブを予告なく破棄する。ソルバーはこれを前提に組む。

- **時間予算とメモリ上限を実行時に決める。** 端末性能を軽いベンチマークで測り、
  探索の打ち切り閾値を調整する。固定値を焼き込まない。
- **打ち切り時は必ず `unknown` を返す。** 予算切れを「解なし」と報告してはならない（§7.6）。
  ヒント機能では「判定できませんでした」と正直に出す。
- **探索は必ず中断可能にする。** Worker へ中断信号を送れるようにし、
  プレイヤーが次の操作をしたら即座に破棄する。ヒント計算でUIが固まってはいけない。
- **進捗を返す。** 数秒かかる可能性があるので、無反応時間を作らない。
- **自動生成はモバイルで走らせない。** 生成は検証を含むため探索の何十倍も重い。
  配布マップは事前生成してリポジトリに含め、
  オンデバイス生成はデスクトップ向けの機能として扱う（もしくは明示的なオプトイン）。

## 8. 自動生成

### 8.1 方針：ランダム生成＋検証は成立しない

ランダムに配置してソルバーで検証する方式は、成功率が低すぎて実用にならない。
**逆向き構築**を採る。先に解を作り、その解が成立するようにマップを組む。

### 8.2 手順

**(1) 骨格生成** — **画面を部屋グラフのノードとして使う**（§3.7）。
`3×3` 画面なら9ノードのグリッドグラフになる。
このグラフ上で開始画面からゴール画面までの主経路を引き、
残りの画面を支道（袋小路）として主経路にぶら下げる。

画面の縁には壁を敷き、隣接画面へ通じる開口部を1〜2箇所に絞る。
これにより画面が閉じた部屋として機能し、**開口部がそのまま関門の設置位置になる**。
画面境界はルール上は何の意味も持たないが、生成の構造としては非常に扱いやすい。

各画面の内部は、1画面に収まる規模の小さなレイアウトとして独立に生成する。
1画面あたりの敵とアイテムの密度に上限を設け、盤面が読み切れる状態を保つ。

**(2) 関門配置** — 主経路をいくつかの区間に切り、境界（＝画面の開口部）に
関門（扉 or 強敵）を置く。区間数がそのままゲームの段数になる。

**(3) 予算計算** — 仮想プレイヤーを主経路に沿って歩かせ、
各関門を突破するのに必要な最小リソースを逆算する。必要分だけを支道に配置する。
**必要量ぴったりに近づけるほど難しくなる**ので、余裕率をパラメータにする。

**(4) オーブ経済の設計** — 祭壇の交換肢と `stock` を決め、
「主経路だけを進むとオーブが足りず、支道の敵を掃討する必要がある」ように敵配置を調整する。
交換肢を排他にすることで一手の重みを作る。

**(5) 囮の混入** — 取ると損をする、あるいは詰む選択肢を混ぜる。

- 割に合わない敵（撃破コスト > 得られる利得）
- 鍵を無駄遣いさせる扉（その先に価値がない、または別の扉が本命）
- 攻撃力を先に取らないと極端に高くつく敵

**(6) 検証と評価** — ソルバーで解を求め、難易度指標を測る。

**(7) 局所修正** — 不合格なら1〜数箇所を修正して再検証する山登り。
シードを固定して再現可能にする。

ここは実装してみて設計を変えた。当初は組み立て時の仮想プレイヤーの精度を上げる方針
だったが、**つまみ（関門の重さ）を 0.35 から 0.92 まで動かしても、締まりは 0.21 から
0.27 までしか動かなかった**。仮想プレイヤーは「置いた敵を全部倒す」前提で計算するのに、
実際の最適解は必要のない敵を素通りするためで、この差は見込みを精密にしても消えない。

そこで方針を変え、**測ってから直す**ことにした。出来上がったマップを解き、
解が実際に通った関門だけを重くして解き直す。通らない敵をいくら強くしても
余ったHPは減らないので、対象を解の上に限るのが要点になる。
刻みは粗→細（4→2→1）で、詰ませたらその敵は諦めて他へ移る。
一度の失敗で全体を打ち切ると、まだ余裕のある他の関門に手が回らない。

副次的に分かったこととして、**オーブ源の敵は反撃を受けない強さ（敵の攻撃力 ≤ 自分の
防御力）にする**。少しでもHPを取る設計にすると、上記の「倒す前提」と「素通り」の差が
そのまま余りになり、見込み7に対して実際68まで開いた。コスト0なら必ず倒されるので
見込みと実際が一致する。オーブ集めは経済の配管であって、考えどころは関門と祭壇にある。

### 8.3 難易度指標

| 指標 | 意味 | 望ましい方向 |
|---|---|---|
| `hpTightness` | 解が**実際に手に入れた**HPのうち使い切った割合 | 大きいほど難しい |
| `hpMargin` | 最適解の終了時HP（参考値） | 小さいほど難しい |
| `greedyFails` | 「解決できるものを全部解決する」貪欲法が失敗するか | 失敗するほど良い |
| `decisionPoints` | 支配関係で潰れない選択肢が2つ以上あった局面の数 | 多いほど考えどころがある |
| `trapCount` | そこから詰みに落ちる手の数 | 適度にあるほど良い |
| `solutionCount` | 最適解の本数 | 少ないほど「解いた」感がある |
| `criticalPath` | 解に必須なオブジェクトの数 | 長いほど段数がある |

`greedyFails` が特に重要である。貪欲法で解けてしまうマップは、
どれだけ大きくても**考える必要がない**。これを不合格条件に入れる。

**余裕は終了時HPの絶対値では測らない。** 初期HPも回復量もマップごとに違うので
比較にならない。かといってマップ上の回復の総量を分母に取ると、最適解が寄らなかった
支道の回復まで「余っている」ことになり、囮を置くほど余裕が大きいと判定されてしまう。
分母は解が実際に集めた分だけにする。

### 8.4 生成器と検証器の関係

生成ループ中は `quick`（ビーム探索）で高速に篩い、
最終候補にのみ `optimal` を走らせる。`unknown`（時間切れ）が返ったマップは
「解けるか不明」であり出荷しない。

- undo / redo

## 10. GitHub Pages でのホスティング

サーバーを持てない前提が設計に効いてくる箇所を明示する。

### 制約と対応

| 制約 | 対応 |
|---|---|
| 静的ファイルのみ。API不可 | 生成もソルバーも全てクライアント側で実行する |
| HTTPヘッダを設定できない | COOP/COEP 不可 → `SharedArrayBuffer` 不可 → 共有メモリ並列なし（§7.8） |
| SPAのパスルーティング不可 | **ハッシュルーティング**を使う。`404.html` フォールバックに頼らない |
| プロジェクトページはサブパス配信 | `vite.config.ts` に `base: '/wwa_puzzle/'`。アセット参照は必ず相対／`import.meta.url` 経由 |
| サーバー保存不可 | 進行状況はローカル保存（キーに base を含めて衝突を防ぐ）。モバイルSafari等ではストレージが自動的に破棄されうるため、**セーブデータのエクスポート／インポート**を必ず用意する |
| マップ共有にサーバーを使えない | URLハッシュに圧縮埋め込み：`#/play?m=<base64url(deflate(json))>` |

### ビルドとデプロイ

- Vite + TypeScript。出力は `dist/`。
- Worker は `new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })` で生成する。
  この形式なら Vite が `base` を考慮したパスを解決する。文字列パス指定はサブパス配信で壊れる。
- GitHub Actions で `main` への push をトリガに、型チェック・テスト・ビルドを行い、
  同じ実行の中の配信ジョブ（`needs: check`）から `actions/deploy-pages` を呼ぶ。
  リポジトリ設定の Pages ソースを「GitHub Actions」にしておく。
- **配信を `workflow_run` で別ワークフローに分けない。** `workflow_run` は
  リポジトリの既定ブランチの文脈で走るため、既定ブランチが `main` でないと
  古いコミットを配信しかねない。実際、空のリポジトリに最初へ push したブランチが
  既定になっていたせいで、配信記録が一つ前のコミットを指したままになった。
  同じ実行の中でジョブを繋げば、この依存が消える。
- `public/.nojekyll` を置く（Actions 経由では Jekyll は走らないが、設定変更時の事故防止）。
- アセットはハッシュ付きファイル名。`index.html` は CDN に短時間キャッシュされる点を許容する。

### 共有と保存で起きたこと

共有URLの読み込みは、当初「壊れた文字列で画面を止めない」ために失敗を握り潰していた。
だがこれは実際に踏むと最悪で、**受け取った側には「開いたのに違うマップが出た」としか
見えない。** 画面は止めないまま、読めなかったことは必ず伝える。

### PWA 化

全アセットが自己完結した静的サイトなので、
Web App Manifest と Service Worker を足すだけでインストール可能・オフライン動作にできる。
モバイルで遊ぶ前提なら、ブラウザUIが消えて盤面に使える面積が増える利点が大きい。

- Service Worker のスコープは Pages のサブパス（`/wwa_puzzle/`）に閉じる。
- 更新時に古いキャッシュが残らないよう、ビルドIDでキャッシュ名を切る。
- Phase 3 以降の任意作業とし、コアの完成を優先する。

### 圧縮埋め込みの実装

`CompressionStream('deflate-raw')` がブラウザ標準で使えるため、外部ライブラリは不要。
URLの長さ制限（実用上 8KB 程度）を超えるマップは共有不可とし、
その場合は JSON ファイルのダウンロードにフォールバックする。

## 11. 描画・UI

対応デバイスはデスクトップ・タブレット・スマートフォンを問わない。
これは後付けできない制約なので、UI設計の出発点に置く。

### 11.1 入力の基本単位を見直す

素朴に考えると入力は「1マス移動」だが、**このゲームでは1マス移動は入力単位として適切ではない**。

§7.2 で述べた通り、自由領域内での移動は状態を一切変化させない。
プレイヤーが実際に行っている意思決定は「次にどのオブジェクトを解決するか」であり、
そこまでの歩数や経路には意味がない。ソルバーが1マス移動を探索単位にしないのと同じ理由で、
UIも1マス移動を入力単位にすべきではない。

したがって入力の基本単位を **「目的地の指定」** とする。

| 対象 | 操作 | 挙動 |
|---|---|---|
| 通行可能なセル | タップ／クリック | そこまで自動経路探索して移動する。**通行可能セルのみを通り、道中で何も解決しない** |
| オブジェクトのあるセル | 1回目のタップ | 選択して情報パネルに完全な情報を表示する（解決はしない） |
| 選択中のオブジェクト | 2回目のタップ | 隣まで自動移動して解決する |
| 解決不能なオブジェクト | タップ | 選択され、理由（HP不足／攻撃不能／鍵不足）を表示する。実行はできない |

この設計は3つの問題を同時に解く。

1. **タッチで快適に遊べる。** 仮想十字キーは指が盤面を隠すうえ、
   移動そのものに意味がないこのゲームでは操作の手数が無駄に増えるだけである。
2. **誤操作でHPを失わない。** 「選択してから実行」の2段構えなので、
   コストの大きい戦闘を誤タップで発動することがない。しかも1回目のタップが
   §11.6 で必要な情報開示そのものになるので、確認ダイアログを別途出す必要がない。
3. **UIとソルバーのモデルが一致する。** ヒント（§7.7）が返すマクロ行動を、
   そのまま「このオブジェクトを選択せよ」として提示できる。

補助として、1マス移動も残す。

- キーボード：方向キー / WASD、`Enter` で選択中の対象を解決
- タッチ：盤面上のスワイプで1マス移動（微調整用）

1マス移動を残すのは、自由領域内でも「どの位置で止まるか」を自分で決めたい場面と、
自動経路探索の結果が意図と違ったときの逃げ道が要るためである。

### 11.2 デバイス非依存のUI規則

以下を破ると、どこかのデバイスで操作不能になる。実装時の不変条件として扱う。

| 規則 | 理由 |
|---|---|
| **ホバーに依存する情報を作らない** | タッチにホバーは存在しない。ツールチップではなく、常設の情報パネルに出す |
| **キーボードショートカットは加速手段に限る** | すべての操作にタップ可能なUI要素を必ず用意する。`左shiftで切替` のような修飾キー専用トグルは、画面上のセグメントコントロールとして実装し、キーはその別名にする |
| **右クリック・長押し・複数指ジェスチャを必須にしない** | 発見されないうえ、プラットフォーム間で挙動が揺れる |
| **タップ対象は実寸 44px 以上を確保する** | タイルが小さい場合、セル選択の当たり判定にヒットスロップを持たせる。細かい対象はパネル側で操作させる |
| **文字は数値の可読性を最優先する** | このゲームの判断材料はすべて数字である。小画面でも数値だけは縮めない |
| **`touch-action: manipulation` / `overscroll-behavior: none` を指定する** | ダブルタップズームと引っ張り更新で盤面操作が壊れるのを防ぐ |
| **セーフエリアを尊重する** | `env(safe-area-inset-*)`。ノッチとホームインジケータにUIを重ねない |

### 11.3 レイアウト

情報量が多いゲームなので、盤面と情報パネルの2領域を、画面の向きに応じて並べ替える。

| 形状 | 配置 |
|---|---|
| 横長（デスクトップ・タブレット横・スマホ横） | 盤面を左、情報パネルを右のサイドバー（参考画像と同じ） |
| 縦長（スマホ縦・タブレット縦） | 盤面を上、情報パネルを下 |

- タイルサイズは `floor(min(利用可能幅 / 画面幅マス数, 利用可能高 / 画面高マス数))` で毎回計算し、
  整数値にスナップする。半端な倍率でのにじみを避ける。
- Canvas のバッキングストアは `devicePixelRatio` を掛けた解像度で確保し、
  CSS サイズと分離する。高DPI端末でぼやけないようにする。
- 縦長では情報パネルの高さが足りないため、優先度で段階的に折りたたむ。
  - 常に表示：自分のHP・攻撃力・防御力・鍵・オーブ
  - 常に表示：選択中オブジェクトの詳細（何も選択していなければ現在画面の敵一覧）
  - 折りたたみ可：敵一覧の全体、全体マップ、what-if 表示
- 1画面のマス数（既定16×16）は、最小想定端末で数値が読める大きさになるかで最終決定する（§14）。

### 11.4 グラフィックの方針

ドット絵素材を用意する手段が無いため、**すべてコードで描画する**。
手書きのSVGパス、または Canvas の描画命令で、幾何形状ベースのスプライトを構成する。
参考画像のような描き込まれたドット絵の質感は再現できない。

ただし、このゲームで視覚に求められるのは絵の魅力ではなく**一目での読み取り**である。
プレイヤーが判断に使う情報は数値（サイドバー）であり、
マップ上のスプライトの仕事は「そこに何が、どのくらいの脅威度であるか」を
視線を止めずに伝えることに尽きる。以下を設計原則とする。

| 原則 | 内容 |
|---|---|
| 種別はシルエットで区別する | 敵・アイテム・扉・祭壇は輪郭の形だけで判別できること。色に頼らない |
| 脅威度は色ランプで表す | 敵の脅威段階を単調な色相／明度のランプに載せる。強い敵ほど強い色 |
| 同一種別は同一形状 | 同じパラメータの敵は必ず同じ見た目。見た目の違いは必ず性能の違いを意味する |
| 状態を重ねる | 「攻撃不能」「HPが足りない」を、スプライトの上に記号オーバーレイで重ねる |
| 色覚多様性に配慮する | 鍵と扉の対応は色だけでなく形（丸／三角／四角）でも区別する |

3番目と4番目が特に重要で、これは絵の巧拙とは無関係にパズルの可読性を決める。
**マップを見た瞬間に「今の自分では通れない場所」が分かる**ことが目標である。

### 11.5 差し替え可能にしておく

描画層は `SpriteId → 描画関数` のレジストリとして抽象化する。

```ts
type SpriteId = string;

interface SpriteRenderer {
  draw(ctx: CanvasRenderingContext2D, x: number, y: number, size: number, state: SpriteState): void;
}
```

初版はコード描画の実装を登録する。後から CC0 のタイルセット（Kenney、DawnLike 等）や
自作素材を入手した場合、画像アトラスから切り出す実装を同じインタフェースで登録し直すだけで
差し替えられる。**ゲームロジックからスプライトへの依存を作らないこと。**

### 11.6 画面分割の描画

§3.7 の通り、カメラはスクロールせず画面単位でスナップする。

- 描画対象は現在の画面のマスのみ。画面外は描かない。
- 画面切り替えは 100〜150ms 程度のスライド演出。演出中の入力は先行入力として蓄える。
- 各辺に、隣接画面が存在すれば方向矢印を表示する。
- 全体マップ（訪問済み画面のみ）をトグルで開ける。
  縮小表示では敵は脅威度の色ドット、アイテムは種別記号のみを描く。

### 11.7 情報開示：すべて見せる

**敵の生パラメータを含め、判断に必要な情報はすべて開示する。**
このゲームは完全情報パズルであり、情報を隠すと推理ゲームに変質して解けなくなる。

情報パネル：

- 自分の HP / 攻撃力 / 防御力 / 鍵（色別本数）/ オーブ所持数
- **現在の画面に存在する敵種別の一覧**。各行に以下を表示する。
  - 撃破コスト（`(n-1) * max(0, de)`）を既定表示
  - `dp <= 0` なら「攻撃不能」
  - `hp <= cost` なら支払い不能であることを色で明示
  - **セグメントコントロール**で、撃破コスト表示と生パラメータ表示（敵HP / 攻撃力 /
    防御力 / 獲得オーブ数）を切り替える。参考画像の「左shiftで切替」に相当するが、
    キーは加速手段にとどめ、切り替えは画面上のタップ可能な要素として実装する（§11.2）。

セル単位の情報：

- **選択したセル**のオブジェクトについて、完全な情報を情報パネルに表示する。
  敵なら全パラメータと撃破コストと撃破後HP、アイテムなら効果量、扉なら必要な鍵。
  選択は §11.1 の1回目のタップ、またはキーボードのカーソル移動で行う。
- **ツールチップ／ホバー表示は使わない。** タッチデバイスに存在しない操作であり、
  常設パネルに出せば全デバイスで同じ情報が得られる。
  デスクトップではホバーで選択をプレビューしてもよいが、それは加速手段にすぎない。

祭壇のUI：

- 交換肢ごとに、コスト・効果・残り `stock`・現在のオーブで交換可能かを表示する。
- **交換後のステータスをプレビューする。** 排他選択が本機構の主目的なので、
  「どちらを選ぶと何が変わるか」を比較できないと判断ができない。
- 縦長レイアウトでは盤面を覆うシートとして開く。
  交換は誤タップの影響が大きいので、ここは選択→確定の2段操作を明示的なボタンで行う。

### 11.8 その他のUI要件

- 進入不可のセルへ移動しようとしたときは、理由（HP不足／攻撃不能／鍵不足）を明示する。
  黙って移動が失敗するのが最悪の体験である。
- **undo は必須。** 一手戻すを状態スナップショットで実装する。
  詰みが不可視なゲームなので、undo が無いと「気づかないうちに詰んでいた」をやり直せない。
  スナップショットは全履歴を保持する（状態は小さいので問題にならない）。
  undo は**常時見えている大きなボタン**として置く。キーボードの `Ctrl+Z` / `Cmd+Z` は別名。
  タッチでの誤操作からの復帰手段がこれしかないため、
  メニューの奥に隠してはいけない。redo も同様に用意する。
- 検討用の「what-if」表示（任意）：攻撃力／防御力を仮に +N したときの撃破コスト一覧。
  順序依存が本体のゲームなので、これがあると計画が立てやすくなる。
  ただしパズル性を下げる可能性があるため、既定オフの補助機能とする。
- キーボード操作のみで全機能に到達できること、
  かつポインタ操作のみで全機能に到達できることを、どちらも満たす。
  一方でしか到達できない機能を作らない。

## 12. テスト戦略

| 層 | 内容 |
|---|---|
| `combat.ts` の単体テスト | 境界値：`dp = 0`、`dp = 1`、`de <= 0`、`n = 1`、`hp == cost`、`hp == cost + 1` |
| `engine.ts` の単体テスト | 各オブジェクト種別の解決、失敗時に状態が変化しないこと |
| ゴールデンテスト | 手書きマップと既知の最適解・終了時HPを固定して回帰を検出する |
| **整合性テスト（最重要）** | ソルバーが返した手順をエンジンで再生し、必ず成立してゴールに到達することを検証する。ソルバーとエンジンの乖離はこのプロジェクトで最も起きやすく、最も痛いバグである |
| プロパティテスト | ランダムな小マップで、全探索の結果とソルバーの結果が一致すること（支配枝刈りの正当性検証） |
| 生成のラウンドトリップ | 生成→検証→シリアライズ→再読込→再検証で結果が一致すること |
| レスポンシブ確認 | Playwright + Chromium で複数ビューポート（スマホ縦／スマホ横／タブレット／デスクトップ）を開き、盤面と数値が読める大きさで収まっていることをスクリーンショットで確認する |
| 入力の等価性 | 主要な操作が、ポインタのみ・キーボードのみのそれぞれで到達できること（§11.8） |

テストランナーは Vitest。CI（GitHub Actions）で型チェック・lint・テストを走らせ、
通過時のみ Pages へデプロイする。
